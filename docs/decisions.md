# Decisions

Choices made where the spec is silent, newest at the bottom of each section.

## Operations and packaging

- **SQLite backups use `VACUUM INTO`**, not the C `sqlite3_backup_*` API. The pure-Go driver only exposes the latter through driver-specific raw connections. `VACUUM INTO` is plain SQL, takes a consistent snapshot inside one read transaction, and produces a compact standalone file. It occupies the single writer connection while it runs, which is negligible at SharedCal's database sizes.
- **Backups are directories, not tarballs.** `sharedcal-<UTC timestamp>/` with blobs hard-linked to the previous backup, so every backup is self-contained and prunable while unchanged blobs cost no space. They are written to `.tmp-…` and renamed when complete. `BACKUP_KEEP=0` keeps everything.
- **`backup.Schedule` returns an error** for an invalid `BACKUP_SCHEDULE` (so startup fails fast) and runs in the background. Runs never overlap, and missed slots are skipped. Schedules use the container's local time (UTC unless `TZ` is set) or a `CRON_TZ=` prefix.
- **Export format is a zip** (random access lets import validate every entry before writing anything) with JSON-lines per table keyed by column name, times in RFC 3339 UTC. `sessions` and `change_log` are excluded. Only the change_log high-water mark is kept, and import advances the sequence past it so reconnecting browsers resync instead of missing events.
- **Import restores files before rows.** A failed row import then leaves only harmless content-addressed blobs and can be retried. The reverse order could commit rows pointing at missing blobs. All rows go in one transaction, except MySQL's `AUTO_INCREMENT` bump, which runs after commit because DDL commits implicitly there.
- **Import refuses unknown tables/columns** (archives from a newer schema) and tolerates missing columns (older archives get zero values). `archive.FormatVersion` is bumped only for incompatible layout changes.
- **The image has no QEMU step.** Builder stages run on `$BUILDPLATFORM` and cross-compile, and the distroless runtime stage has no `RUN`, so multi-arch builds are fast.
- **S3 storage uses `minio-go`**, not the AWS SDK: it is much smaller (a smaller `govulncheck` surface) and targets S3-compatible servers, not just AWS. `S3Store` hashes every blob before uploading it, so a key can never point at other content. It doesn't rely on the server checking an `x-amz-checksum-sha256`, which not every S3-compatible server supports. Downloads are proxied through the app (seeks become ranged GETs) instead of redirecting to presigned URLs, so the session check and the sandboxing headers still apply and the bucket stays private.
- **With `BLOB_STORE=s3`, `sharedcal backup` leaves attachments out**, and its manifest says so. Copying every object into each backup would be slow and costly; bucket versioning or replication protects content-addressed blobs better. Export still includes every referenced blob.
- **Export reads blobs by the keys the database references** (attachments, thumbnails, the logo) instead of walking a directory, so it works with any blob store and leaves unreferenced files out. Blobs that are already gone (infected uploads keep their row) are skipped. Archives keep format version 1; `files/` entries from older archives are still restored into `DATA_DIR`.
- **Drop-in theme files are copied into the database at startup** instead of being read from `DATA_DIR/themes` on every request, so a PostgreSQL/MySQL + S3 instance needs no data volume. A file is written when its theme is missing or differs from the stored copy. Removing such a theme in Settings only lasts if its file is removed too.
- **Atlas lives outside the main module** (`tools/atlasloader` with its own `go.mod`, config in `deploy/atlas/atlas.hcl`) so the app's dependency graph and `govulncheck` surface don't include Atlas. Because the GORM models don't declare FKs or CHECKs, Atlas output must be reviewed so it doesn't drop them.

## Deviations from the stack table

- **SQLite migrations run through a small in-repo golang-migrate driver** (`internal/store/migrate_sqlite.go`). golang-migrate's bundled `sqlite` driver imports `modernc.org/sqlite`, which registers the same `database/sql` name as `glebarez/go-sqlite` (used by the GORM dialector), so the two cannot be linked into one binary. PostgreSQL and MySQL use golang-migrate's own `pgx/v5` and `mysql` drivers, and their advisory/`GET_LOCK` migration locks.
- **The initial migration was generated from one table description** (`tools/schema-gen.py`) rather than by Atlas, so that FKs and CHECK constraints are identical in all three dialects. Later migrations can be generated with Atlas (see CONTRIBUTING.md) and must be reviewed. `TestModelsMatchMigrations` fails if a model and the schema drift apart.
- **Repositories are not a separate layer.** `internal/store` holds the models and connection handling; the domain services query GORM directly inside their transactions. A repository layer would only forward calls at this size.

## Data and schema

- **Three columns beyond the spec's table:** `events.series_end_at` (end of the last occurrence, so range queries can skip finished series), `events.deleted_by_id` (for the owner's undo window), `notifications.event_id` and `activity.event_id` (so the inbox and an event's History tab need no joins through polymorphic subjects), and `change_log.audience_user_id` (so per-user messages are filtered on replay too). `sessions.last_seen_at` throttles idle-extension writes.
- **`activity` has only `created_at`**: it is append-only, so `updated_at` would always equal it.
- **MySQL tables use `utf8mb4_bin`.** Case-insensitive collation would make OIDC subjects that differ only in case collide (and match each other in lookups). Tag-name uniqueness is case-insensitive and is enforced by the application instead.
- **Mentions are stored as notification rows** (`kind = comment.mention`), not a separate column; the comment DTO's `mentions` list is read from them.
- **Times read back from the database are always in `time.UTC`.** MySQL gets `loc=UTC` in its DSN; PostgreSQL connections set the session time zone to UTC and register a `timestamptz` codec that scans into UTC, because pgx otherwise returns `time.Local` and API output would carry the server's offset.
- **Event times are truncated to whole seconds** (calendar granularity; keeps text-encoded SQLite timestamps comparable).

## Behavior

- **Bootstrap admin is pinned** (`role_source = manual`), so a later IdP group recompute cannot demote the only way into a fresh install. `BOOTSTRAP_ADMIN_EMAIL` only matches when the IdP says `email_verified = true`.
- **Last-admin protection also applies to IdP recomputes**: if a login would demote the last active admin, the admin role is kept and a warning is logged.
- **Settings' default role** (Settings page) overrides `DEFAULT_ROLE` for new users whose groups match nothing; `DEFAULT_ROLE` is the initial value.
- **The settings attachment size limit cannot exceed `ATTACHMENT_MAX_SIZE`**, because proxies and the HTTP layer are sized for the environment value.
- **Recurring-event editing.** A single occurrence ("this event") can change title, description, location, status, start and end. Changing the time zone, all-day flag, rule or tags needs "this and following" or "all". Deleting one occurrence adds an `EXDATE` (and drops its override); `event_overrides.cancelled` is kept for CalDAV import. Moving a whole series shifts its EXDATEs and override `RECURRENCE-ID`s by the same amount so exceptions stay attached. "This and following" splits the series: the head gets `UNTIL`, and the tail is a new event (new UID) with the remaining `COUNT`, the later overrides and the later EXDATEs.
- **Allowed RRULEs:** DAILY/WEEKLY/MONTHLY/YEARLY only, no BYHOUR/BYMINUTE/BYSECOND/BYEASTER, `COUNT ≤ 5000`, `INTERVAL ≤ 1000`, `UNTIL` within 200 years, and the rule must occur at least once within 8 years. These bound expansion cost against hostile input. A range query returns at most 2,000 occurrences per event and spans at most 400 days.
- **Changing only an event's time zone keeps its wall-clock times** (19:00 stays 19:00 in the new zone).
- **Owners can undo a delete for 60 seconds** on the server; the UI shows the toast for 10. After that, only admins can restore, for 30 days. An hourly maintenance job then purges events and attachments, and deletes blobs that nothing references any more.
- **Suggestions are always against the whole series** (`scope = all`). A suggestion whose `baseVersion` is older than the event is refused with 409 and the current event, so the author proposes against what is actually there. Conflict flags then cover edits made between proposing and reviewing. Accepting a suggestion is recorded as a normal edit by the reviewer plus a `suggestion.accepted` activity row that names the suggester and the accepted fields.
- **Writers can delete attachments they uploaded** while they are still writers, as the API table's "Uploader, event owner, Admin" says. A demoted uploader can no longer remove them.
- **Thumbnails are served with the normal session check**; the optional signed thumbnail URLs were not needed because thumbnails are same-origin `<img>` requests that carry the session cookie.
- **Session IDs shown on the People page are the first 16 hex characters of the stored hash**: enough to revoke one, useless as a credential.
- **CSRF** is a session-bound HMAC token delivered by `GET /api/me`. Non-GET requests must send it in `X-CSRF-Token`, and it must also match a `SameSite=Strict` cookie (double submit) and come with a same-origin `Origin` (or `Referer`) header. Cookies get the `__Host-` prefix and `Secure` only when `APP_URL` is https, so local http development works.
- **CSP allows `style-src 'unsafe-inline'`**: FullCalendar and Radix set inline `style` attributes for positioning. Scripts stay `'self'` only, and the no-flash theme bootstrap is an external file.
- **SSE payloads are personalized per recipient**: the broker fans one message out, and the stream handler recomputes `permissions` for each user (role cached for 10 s, dropped at once on `user.role_changed`). The `change_log` always keeps its newest row, so a reconnecting client can tell "up to date" from "missed pruned changes" (→ `resync`). Writes are serialized with publishing so messages leave in `seq` order.
- **Upload, download, stream and logo endpoints are plain handlers**, so uploads stream without buffering. They are added to the generated OpenAPI document by hand (`documentRawOperations`).
- **The ICS feed covers one-off events that ended in the last year and every series that hasn't ended.** Feed paths are redacted from request logs. Events in the trash (deleted within the 30-day purge window) stay in the feed as `STATUS:CANCELLED` with a bumped `SEQUENCE`, because some subscribers (notably Google Calendar) don't reliably drop events that just vanish. These entries carry only the UID, times, RRULE, SEQUENCE and LAST-MODIFIED, never the title, description, location or tags.
- **Erasing a user ("hard-delete their data") anonymizes the row instead of deleting it.** `DELETE /api/users/{id}` deletes the user's comments, uploads (blobs included), suggestions, inbox, preferences, feed token, sessions and personal change-log rows, and blanks the audit snapshots of that content and of the user record. The `users` row stays as "Deleted user" (email, avatar and groups cleared, `erased_at` set), because `activity`, `events.owner_id` and reviewers reference it. Its OIDC issuer and subject are cleared too, so signing in again creates a fresh account rather than reviving the old one. Live events must go to another writer or admin in the same request (`transferTo`); trashed ones stay attributed to "Deleted user" until the 30-day purge. A comment that others replied to keeps an empty, deleted row so their replies stay threaded. Change-log rows broadcast to everyone may still name the user until they are pruned (24 h). Admins cannot erase themselves.
- **Removed attachments are restorable only while their event is live and their comment (if any) still exists.** `GET /api/trash/attachments` lists exactly those, and restoring one whose comment was deleted meanwhile returns 409.
- **Presence messages leave out their recipient**, so a client never has to filter itself out.
- **Ownership changes always apply to the whole series**, whatever `scope` says, and the Details tab offers them to admins as a separate control rather than as part of the edit form.
- **`mockoidc` (dev/e2e only)** binds to 127.0.0.1, only redirects to loopback `/auth/callback` URLs and requires PKCE.

- **Event types implement and extend the spec's planned "event categories".** The name follows the feature request ("types"), and it adds what the spec lacked: a list of predefined fields per type that replaces the free-form description. Differences from the spec sketch: the URL filter is `?types=`; and the table is `event_types` with `events.event_type_id` and `events.fields_json`.
- **A single occurrence can have its own type** (movie or game releases in a weekly series). The override row gets `type_overridden`, `event_type_id` (NULL = generic) and `fields_json`; when `type_overridden` is set they replace the master's type and values as a unit, never field by field. Changing only the fields of an untouched occurrence copies the master's type into the override first. A typed occurrence has no description; going generic again drops the override's description so it inherits the master's. The type filter and text search are decided per occurrence for series that have any type override (otherwise a search for one release would return the whole series). The year counter follows the occurrence's type. Types used by an override can't be deleted either. In the ICS feed an overridden occurrence's `DESCRIPTION` is its own field summary; its `CATEGORIES` still come from the master.
- **Typed events store values by field key in `events.fields_json`.** Keys are generated once and never change, so renaming a label keeps values. Removing a field (or changing its kind) leaves stored values in place but hidden; they are dropped the next time the event's fields are saved. Edits that don't touch `fields` are never re-validated against the type, so adding a required field later doesn't lock existing events.
- **Type styles are `sc-style-*` classes with CSS in `index.css`.** FullCalendar only applies classes we hand it, so `banner` (filled, bold strip), `outline` (inset border, normal text) and `badge` (icon in an inverse-colored chip) are descendant-selector rules that read the type's `--fc-event-color`. `default` and `badge` differ only in the icon chip. The spec's "styles are theme tokens" is met only as far as the colors are: a theme can't restyle the shapes yet.
- **Banner events sort first within a day** in every view (a custom `eventOrder`), so in the agenda they form a strip right under the day heading. They are not rendered inside the heading itself: FullCalendar's list view has no hook for content there.
- **The year counter is computed on the server from the series' own start date**: `yearsSince = year(occurrence) − year(first start)` in the event's zone, sent only for recurring events whose type has `yearCounter`, and only from the second year (a series created today shows nothing). "Off unless the series started in a real year" therefore means a yearly event has to start on the real birth date or wedding date. A "this and following" split starts a new series, which restarts its count.
- **Creation defaults now include the length of timed events** (`defaultDurationMinutes`, 0 for instants such as deadlines), applied by the full form and the quick-create popover. Quick create has a type picker; a type with required fields disables the Create button there and points to More options. Presets (Birthday, Anniversary, Holiday, Deadline, Reminder) live in the web app and are created through the normal API, so an admin edits them like any other type.
- **A type that events still use can't be deleted** (409), unlike the spec's "events become uncategorized". Silently discarding every event's field values seemed worse than asking an admin to move the events first. Trashed events count, because restoring one must not break.
- **Typed events have no description.** The API refuses one, and switching an event to a type clears its description. Creation defaults (all-day, repeat) are applied by the client when a type is picked; the server stores what it is sent.
- **The type's color wins over the first tag's**, as the spec says; tags still filter and group. Chips also carry the type's icon and the screen-reader label starts with the type name, so the look never depends on color alone.
- **A `members` field kind stores a list of user ids**, picked from the user directory. Ids must belong to existing users, but inactive or erased ones stay valid so old events remain editable; the UI shows "Unknown person" when it can't resolve an id. The ICS feed writes their names.
- **The ICS feed shows a typed event's field values as `Label: value` lines in `DESCRIPTION` and the type name as a `CATEGORIES` entry.**

## Frontend

- **URL is the source of truth for calendar state**: `?view=&date=&event=&occurrence=&tab=&q=&tags=&types=&owners=`. The view the user picks is also saved as `preferences.defaultView` (except the automatic Agenda default under 768 px).
- **Live cache patching is pure** (`web/src/realtime/applyMessage.ts`, unit-tested). Single events are patched into every cached range they overlap and removed from ranges they left. Recurring series and free-text searches are refetched. Stale versions are ignored. The 600 ms glow skips the user's own writes.
- **Optimistic drag and drop**: the cache is patched before `PATCH`. A failure rolls back; a 409 also stores `problem.current`.
- **The event side panel, forms (Zod, React Hook Form), Markdown, the lightbox and all secondary pages are lazy-loaded** to keep the first load under 300 KB of gzipped JS (`npm run check:size`).
- **Tag text colors are computed, not themed**: each `--tag-N-foreground` is white or near-black, whichever reaches 4.5:1 on that theme's tag color. CI checks this.
- **The rail expands on hover after 200 ms** (hover intent), on keyboard focus, or when pinned. Pinning pushes the content; hover overlays it.
- **Forms edit the version they were opened on.** Live updates keep re-rendering the side panel; the event form ignores them, so a save after someone else's change gets the 409 and the conflict dialog instead of silently overwriting it.
- **Preference changes are saved one at a time**, each sending the latest cached preferences, so quick successive changes (e.g. clock, then week start) cannot overwrite each other.
- **Admin routes render Not Found for non-admins** instead of a page whose data fails to load. The API refuses the data either way.
- **End-to-end tests sign each user in once per run** and reuse the session, because `/auth/*` is rate-limited per IP and the whole suite comes from one address. `E2E_PORT` and `E2E_OIDC_PORT` move the test servers off 8080/9999 so the suite can run next to `make dev`.
- More frontend assumptions and API gaps are in `docs/frontend-notes.md`.
- **Title templates generate titles on the server and are stored in `events.title`.** A type's `titleTemplate` (`{{field_key}}` placeholders over text, number, choice and people fields) renders on every create and edit; a title in the request is ignored, so ICS, search and notifications keep reading the stored title. Changing a template or fields retitles the type's events in the same transaction (bumping their version) and clears occurrence titles that only inherited the series' values. Occurrences with their own type values store their own generated title. People fields are stored by user id and rendered with the person's current name; when a name changes (IdP login) or a user is erased, the titles that mention them are regenerated, and clients pick the new titles up on their next fetch. Date and checkbox fields are excluded because their rendering depends on locale. The client mirrors the rendering in `lib/titleTemplate.ts` only for the live preview.
- **A type's all-day and repeat settings are rules, not defaults.** `defaultAllDay` means every event of the type is all-day, and a non-empty `defaultRrule` means every event repeats with exactly that rule; an always-all-day type can also set `singleDay`, which limits events to one date (end = start + 1 day), independently of the repeat rule. The server rejects violations on create, on a type change and whenever an edit touches allDay, rrule, start or end (422 with the field named); unrelated edits to an older, non-conforming event still work. The form shows the fixed settings as locked text instead of controls, and the calendar stops dragging such chips into the timed grid or stretching single-date ones. Internal probes that build partial inputs skip the check.
- **Moving the year of one occurrence of a year-counting series sets the year the series began.** "All events" otherwise shifts the whole series by the same amount, which moves the first occurrence too and leaves the count unchanged (or inflated: 2026 → 1995 on a 1990 series made 2026 read as 72). For yearly series of a type with `yearCounter`, only the day within the year shifts exceptions and overrides; the series start takes the edited year.
- **"Never repeats" is its own flag (`neverRepeats`), not a sentinel rule.** An empty `defaultRrule` already means "chosen per event", so forbidding repetition needs a separate value; the two are mutually exclusive (422 when both are set). It is enforced like the other fixed timing settings: on create, on a type change and when an edit sends `rrule`. The admin repetition select offers it as "Never repeats" and the form shows "Does not repeat" instead of the recurrence picker.
- **Single date is its own setting (`singleDay`), not implied by all-day plus a repeat.** The implied rule left all-day + never-repeats (releases) open to ranges while all-day + yearly (birthdays) was one date, with no way to say which a type wanted. Timing now has three independent choices: always all-day (with Length: one or more days / single date), repeat (chosen per event / always a rule / never), and nothing else; multi-range events are not a thing. Migration 0007 sets `single_day` on existing types that were all-day with a fixed repeat, so they behave as before.
- **Title templates have optional parts, written `{{#field}}…{{/field}}`, and there is a `time` field kind.** A part is kept when its field has a value and dropped, tags included, when it does not; parts may nest. Tags must pair up, every field named must be a text, number, time, choice or people field, and at least one placeholder must sit outside every optional part so a title can never come out empty. Times are stored as `HH:MM`, a wall time in the event's own time zone. The stored title (search, history, notifications) shows them as `HH:MM` in that zone; everywhere a person reads a title they see the time converted to their own zone and 12/24-hour setting. The web client rebuilds such titles for display (`useEventTitle`), and each ICS feed does the same server-side from its owner's preferences, using the occurrence's date for daylight saving; a recurring series' single summary uses its first date. Only the time is shown, so a conversion across midnight reads as the other day's time. The form shows the zone beside the time, and shows the time zone picker for all-day events whose type has a time field. There is no inverse section yet.
- **Events of an ownerless type belong to a reserved system user, not a null owner.** `events.owner_id` is `NOT NULL` with a foreign key, and SQLite can't relax that without rebuilding the table (which would cascade-delete comments, attachments and suggestions while foreign keys are on). The system user (`store.SystemUserID`) is an inactive viewer created on first use; it is hidden from the directory and the admin user list, can't be changed or erased, and never receives notifications. Nobody owns its events, so only admins edit them and writers get "suggest". Ownership is decided when an event is created (including by import) and isn't recomputed if the type changes later; an admin can still transfer an ownerless event to a person.
- **ICS import is one admin-only endpoint with a dry run, and dedupes on the file's UID.** `events.source_uid` records the VEVENT UID, so importing a file again skips what is already there instead of duplicating it (events in the trash don't count). Each row goes through the normal create path, so the chosen type's rules (all-day, fixed repeat, required fields) apply and violations are reported per row rather than failing the file. EXDATE, RECURRENCE-ID overrides and cancelled events aren't imported.
